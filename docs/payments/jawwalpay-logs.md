# سجلّ جوال باي — قراءة الطلب والرد

كل نداء إلى البوابة يُكتب الآن **كاملاً**: الـ JSON الذي أرسلناه، والـ JSON الذي
عاد، ومعهما رمز الخطأ ووصفه. ومعها أسطر جديدة لما يحدث **قبل** النداء — لأن
الرفض قبل النداء هو ما كان يمرّ بلا أثر.

## أين

في سجلّ التطبيق كما هو:

```sh
grep jawwalpay storage/logs/laravel.log | tail -40
```

ولملف خاص لا يحوي غيره — مفيد أثناء متابعة دفعة حقيقية:

```env
JAWWALPAY_LOG_CHANNEL=jawwalpay
```

```sh
php artisan config:clear
tail -f storage/logs/jawwalpay-$(date +%F).log
```

لإطفاء التسجيل كلّياً: `JAWWALPAY_LOG=false`.

## شكل السطر

```
[2026-09-28 11:55:19] production.INFO: jawwalpay.v1/business/send_otp
{
  "msgId":"96518815279349",
  "errorCd":"00",
  "desc":"نجحت",
  "meaning":"تمت العملية بنجاح",
  "ref":"2922813401869",
  "request":"{\"msgId\":\"96518815279349\",\"receiver\":\"009705••••4077\",\"amount\":\"3\",\"lang\":\"AR\",\"secureHash\":\"…\"}",
  "response":"{\"errorCd\":\"00\",\"desc\":\"نجحت\",\"extraData\":[],\"ref\":\"2922813401869\",\"statusCode\":\"1\"}"
}
```

- **`errorCd` + `desc`** من البوابة، **`meaning`** ترجمتنا للرمز نفسه — لأن `desc`
  يتبع `lang` وقد يأتي مقتضباً أو بالإنجليزية.
- **`request`** الحمولة كما خرجت، بما فيها `secureHash` — وهو ما يطلبه دعم جوال
  باي أولاً. رقم المحفظة مقنّع، ورمز التحقق مستبدل بـ`[otp]`.
- **`response`** الظرف كما عاد بلا حذف، عدا توكن الجلسة إن ظهر.

**لا يُكتب أبداً:** المفتاح السري، توكن الجلسة، ولا الرمز الذي أدخله الزبون — ولا
حتى بصمته، فهي تقوم مقامه.

## الأسطر الأربعة لدفعة واحدة

| السطر | متى | ماذا يعني |
|---|---|---|
| `jawwalpay.v1/business/send_otp` | عند طلب الرمز | البوابة أرسلت الرمز (أو رفضت) |
| `jawwalpay.checkout.code-sent` | بعده مباشرة | حفظنا نية الدفع: `amount` بالأغورة و`msgId` |
| `jawwalpay.checkout.charging` | عند `POST /orders` | **سنسأل البوابة الآن** |
| `jawwalpay.v1/business/MFP` | بعده | جواب البوابة على الخصم |

## القراءة المهمة: من رفض؟

هذا هو السؤال الذي لم يكن السجل يجيبه. القاعدة:

> **إن لم يظهر `jawwalpay.checkout.charging`، فالبوابة لم تُسأل أصلاً — نحن من
> رفض.** والسبب مكتوب في `jawwalpay.checkout.refused`.

```
[…] production.WARNING: jawwalpay.checkout.refused
{"reason":"amount-changed","wallet":"009705••••4077","approved":300,"total":1500}
```

| `reason` | ماذا حدث | ما العمل |
|---|---|---|
| `request-validation` | الحقول لم تجتز التحقق؛ `errors` يسمّي الحقل | غالباً الفرونت أرسل شيئاً ناقصاً أو بصيغة غير متوقعة |
| `missing-code` | لم يصل رقم المحفظة أو الرمز | الفرونت لم يرسل `jawwalPhone` أو `jawwalCode` |
| `no-otp-requested` | لا توجد نية دفع محفوظة لهذه المحفظة | إمّا أن `send-code` لم يُستدعَ، أو أن رقم المحفظة اختلف بين النداءين، أو **أن الكاش لا يعمّر بين طلبين** — انظر `cache` في السطر نفسه |
| `amount-changed` | الرمز أُرسل لمبلغ والطلب صار مبلغاً آخر | قارن `approved` بـ`total` — كلاهما **بالأغورة** (1500 = 15.00 ₪) |
| `gateway-refused` | البوابة رفضت الخصم | الرمز في `errorCd`، وسطر `MFP` قبله يحمل الرد كاملاً |
| `no-answer` | سألنا ولم يصلنا ردّ | الطلب يبقى ومحاولة الدفع «غير مؤكدة» — **لا يُعاد الخصم** قبل مراجعة بشرية |

### `no-otp-requested` وحقل `cache`

نية الدفع تُحفظ في الكاش لعشر دقائق بين `POST /orders/jawwal/send-code` و
`POST /orders`. إن كان `cache` في السطر يساوي **`array`**، فالكاش لا يتجاوز الطلب
الواحد ولن تنجو أي نية بين النداءين — وستُرفض **كل** دفعة تلقائية بهذا السبب.
العلاج:

```env
CACHE_STORE=file        # أو redis / database
```

```sh
php artisan config:clear
```

## أكواد الأخطاء المتكرّرة

| الرمز | المعنى | المصدر |
|---|---|---|
| `00` | نجحت | — |
| `46` | رسالة مكرّرة (`msgId` مُستهلَك) | نولّد رمزاً جديداً لكل محاولة، فظهوره يعني إعادة إرسال |
| `88` | انتهت صلاحية رمز التحقق | الزبون تأخر — يطلب رمزاً جديداً |
| `89` | رمز التحقق غير صحيح | الزبون أخطأ في الإدخال |
| `91` | انتهت الجلسة | نعيد تسجيل الدخول ونكرّر النداء تلقائياً مرة واحدة |
| `1004` | `secureHash` غير مقبول | [صيغة التوقيع](./jawwalpay-securehash.md) |

الجدول الكامل في `App\Services\JawwalPay\ErrorCode`.

## ما تُرسله للدعم

سطر `MFP` أو `send_otp` كاملاً: فيه `msgId` و`ref` و`errorCd` والحمولة الموقَّعة.
هذا كل ما يحتاجه أحمد عمرو للبحث عن العملية عندهم.
